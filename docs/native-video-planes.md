# Native video planes: opt-in prototype

This prototype connects FFmpeg decoding to Vulkan rendering through neutral immutable values. The earlier independent painter passed hosted tests; the current candidate adds the real desktop paint path behind an explicit, default-off opt-in. Existing `MediaFrame`, `ImageData`, default playback, previews and posters keep their RGBA contracts. Integration source alone does not establish compilation, integrated GPU correctness, memory savings, 60 fps, VM behavior or the whole-shell 300 MiB target.

The earlier same-source retarget experiments preserved decoder sessions but had variable retained-heap results. They remain separate evidence. This prototype explores removing RGBA conversion and publication storage, without changing the allocator or weakening source admission.

## Concrete path and boundaries

1. The independent `native-video-planes` example calls the existing `WallpaperPlaybackPort::prepare`. The real adapter imports immutable media and writes its validated poster/descriptor. It never fabricates an asset.
2. It explicitly calls the optional `play_native`. Existing adapters get a default implementation that delegates to RGBA playback with the same cadence, loop and target options; ordinary clients still call `play`.
3. `NativeVideoWallpapers` uses the existing bounded input, source clock, H.264 frame-thread configuration, EOF draining/rewind, callback stop and cancellation logic. The core delivery seam can carry either existing RGBA or `NativeMediaFrame::Yuv420`.
4. `video/native_planes.rs` admits only the supported native subset. Its FFmpeg ownership and unsafe access stay inside the concrete adapter.
5. `lucent-video-frame` is a small shared crate with checked `Plane` and `Yuv420Frame` values, explicit BT.709 range/transfer/chroma metadata, and immutable `Bytes` owners. It depends only on `bytes`; neither domain nor framework gains a codec, OS or GPU dependency. The API and domain re-export the same values.
6. `PlanarPainter` receives these values through the framework API. It uploads three reusable R8 textures, samples them in a shader, and draws one opaque video into the existing nonlinear-sRGB `Bgra8Unorm` target. Geometry or output-size changes do not require a new decoded source extent. No compositor calls or service operations enter a view.

The independent painter fills its validation target. The current integration candidate below separately routes immutable descriptors through the actual component/layout/scene path, while preserving the default RGBA desktop. Neither path establishes native session or performance acceptance.

## Ownership and initialized bytes

The adapter checks all visible plane spans against real `AVBufferRef` owners before constructing a slice. It rejects invalid bounds and falls back for nonpositive strides. Admission **consumes the owned decoder frame**, moving its existing AVFrame and buffer references into a private immutable owner. Unsupported capability returns that same owned frame for software conversion. Neither `av_frame_ref` nor `Video::clone` is needed. A borrowed admission helper would leave the caller's mutable `Video` alive; its safe `data_mut` method does not enforce copy-on-write, so merely retaining another AVFrame header would not establish Rust immutability. [FFmpeg's frame API](https://ffmpeg.org/doxygen/trunk/group__lavu__frame.html) documents its reference ownership and writable-buffer protocol.

A packed plane (`stride == visible width`) can publish a `Bytes::from_owner` view. Its private owner retains the consumed AVFrame; no safe mutable Rust frame handle remains. The FFmpeg decoder's own reuse must respect the outstanding AVBuffer references. Returning from the decoder does not invalidate retained planes; the final byte owner releases its references. [Bytes' ownership API](https://docs.rs/bytes/1.12.1/bytes/struct.Bytes.html#method.from_owner) keeps the supplied owner alive through retained views.

Allocated padding is not assumed initialized. Every padded plane instead copies only visible samples row by row into a packed buffer. No slice spans uninitialized row gaps. `referenced_bytes` and `copied_bytes` report these publication choices, not the full underlying AVBuffer allocation or process memory. Retained buffers can outlive decoding; consumers remain responsible for limiting retained frames. Normal streaming has no CPU RGBA publication in the admitted native branch, but GPU upload still uses wgpu staging copies. This is not zero-copy GPU import or hardware decoding.

For an even 3840×2160 source, visible YUV4208 occupies 12,441,600 bytes; RGBA8 occupies 33,177,600. These are arithmetic payload sizes, not measured memory savings. Decoder reference frames, allocator arenas, staging, target buffers and driver memory are additional costs.

## Explicit color contract

Admission requires progressive 8-bit YUV420P, square pixels, no crop or decode error, explicit BT.709 matrix and primaries, known full/limited range, BT.709 or sRGB transfer, and left/center chroma siting. ICC, mastering, light-level and display-transform side data fall back. Unsupported/untagged/alpha formats retain the existing software RGBA branch; this prototype has no default color guess for ordinary untagged videos.

The shader removes the range offset, reconstructs nonlinear RGB with the BT.709 matrix, then converts a tagged BT.709 transfer to sRGB. BT.709 and sRGB share the supported primaries and D65 white; this subset needs no chromatic-adaptation matrix. The BT.709 curve follows FFmpeg's continuous coefficients, and sRGB encoding follows W3C's conversion. [FFmpeg color utilities](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavutil/csp.c), [W3C sRGB conversion](https://www.w3.org/TR/css-color-4/#color-conversion-code).

Lucent's current image textures use `Rgba8Unorm`, and its shader pipeline, snapshot target and actual Wayland `SurfaceConfiguration` use `Bgra8Unorm`. The video shader therefore writes **nonlinear sRGB code values**. Using this painter with an sRGB attachment would apply the transfer twice and is outside its contract. This does not establish color-managed output or HDR support. The old software RGBA converter may preserve a different transfer; byte equality to that converter is not the oracle for correctly tagged BT.709 conversion.

Chroma coordinates derive from luma sample coordinates, explicit siting offsets and ceil-sized chroma planes. Reusing normalized luma UVs for odd extents would shift the chroma at edges. The current candidate explicitly loads four R8 texels per plane and interpolates in float32, clamping at each actual plane boundary. Its twelve loads per output pixel have a performance cost; there is no 60 fps or memory-gain claim. `Queue::write_texture` accepts checked non-256-aligned row strides; the separate readback path retains its required padded-buffer alignment. [wgpu layout requirements](https://docs.rs/wgpu-types/30.0.0/wgpu_types/struct.TexelCopyBufferLayout.html).

This is **one-level bilinear sampling**, with no mip chain or proper minification filter. The small odd-size/downscale test checks coordinates and color math; it does not establish high-frequency image quality for 4K→small viewports. Production integration must preserve proper minification, HiDPI density and chroma siting, with actual downscale/odd-edge checks and native whole-path measurements. Reducing quality to meet the memory target is not an accepted tradeoff.

## Validation scope

Authored tests cover checked odd geometry/strides, shared owner lifetime, matrix/range/transfer anchors, FFmpeg buffer bounds before slicing, consumed packed ownership and retained immutable clones, padded-row copies, exact fallback-handle return, real tagged-H.264 EOF/timing/rewind/cancellation without RGBA scratch, and unchanged RGBA fallback pixels/timestamps. The example's parser stays inert without explicit `--run` and rejects ambiguous paths.

Three explicitly ignored `video_planes_gpu_` tests exercise actual Vulkan texture sampling, independent f64 color/resampling expectations (matrix derived from luma weights), both transfers/ranges, odd edges/strides/siting, scaling, opaque output and texture reuse. They permit one output-code step for quantization/interpolation and are added to the existing hosted Vulkan suite. They have not been run locally. Old RGBA visual tests remain required, and no existing goldens/catalogue hashes were refreshed.

The first compiled source, `e97c5c4`, passed hosted Clippy/workspace/protocol gates and all 18 new non-GPU tests. On actual llvmpipe Vulkan, two new GPU tests passed; the odd/scaled case failed the unchanged one-code tolerance with blue 54 versus the independent expected 52. A model using quantized interpolation fractions and staged UNORM rounding reproduces that result, which **suggests** filtered-R8 precision as a cause; the driver's exact algorithm is not proven. The subsequent explicit float32 candidate passed those same independent tests; the original failure remains recorded. No tolerance was raised. [Recorded hosted failure](https://github.com/xandreeddev/desktop-lab/actions/runs/40442642028/job/121986350957).

Source `c4a87237ab96b41d0013265e3d8043286e18d64e` subsequently passed hosted fmt, workspace/all-target Clippy, workspace tests, protocol suites and the configured legacy Vulkan suite. All 21 new test names, including the three strict GPU cases, were individually verified. The GPU was llvmpipe CPU Vulkan; this is not native Wayland presentation or hardware performance acceptance. The site job passed; the overall workflow failed the unchanged Component Lab production-input roster. Its old architecture guards also needed an explicit role for the new neutral value crate; the integration branch adds constrained dependency checks and negative fixtures, with 30 Python architecture tests executed successfully. [Actual c4a hosted Rust result](https://github.com/xandreeddev/desktop-lab/actions/runs/40444349431/job/121991926419).

The independent example can be run in an explicitly owned environment:

```sh
cargo run --manifest-path lucent/Cargo.toml --locked -p native-video-planes -- \
  --run --source /absolute/tagged-video.mp4 \
  --state /absolute/new-plane-test-store --output /absolute/new-plane-test.png
```

It stops after the first frame, waits for the decoder body to return, then draws retained native planes with Vulkan and writes a validation-only PNG. Unsupported input writes the established RGBA fallback and prints that distinction. The RGBA snapshot/readback is deliberately excluded from any future normal-stream allocation claim. It creates an explicit import store but never selects a wallpaper or changes a running session.

## Experimental desktop paint path

The integration candidate carries checked `Yuv420Frame` values through `ImageStream::frame_yuv420` into immutable `VideoData`. The declarative client builds `Element::video`; layout emits `Paint::Video` using the same cover/contain geometry, rounded and diagonal clipping, tint and opacity as images. Rendering shares the existing 64 MiB soft resource cache, texture liveness and scene pinning rules. Native textures and uniforms contain no `Rc<Gpu>` cycle; temporary CPU frame owners live through deferred uploads, then submission commits only weak lifetime and stream revision metadata. Live resources may exceed the cache's soft budget, as with existing RGBA scenes; it is not a process-memory limit.

The client keeps its bounded latest-frame mailbox and one stream identity across RGBA/native fallback. A frozen paused or outgoing frame shares immutable plane ownership but has independent GPU identity. Source timestamps, producer-revision rejection, last-good error presentation, source/FPS changes and output retirement retain the existing coordinator semantics. This does not add worker joins to UI code or establish strict non-overlap between replacement decoder workers.

Native playback is off by default. For an explicitly owned test session, the composition root accepts `LUCENT_NATIVE_VIDEO_PLANES=1`; there is no persisted preference or automatic enablement. Only a player routed to one known output with known physical cover demand can request planes. Shared, mixed and unknown output routes use existing RGBA playback, including when a stale target exists before output enumeration. The playback adapter independently checks the actual target against source extent: any minification returns the existing fitted RGBA bytes/aspect/timing. Unsupported color metadata and alpha formats also preserve RGBA. This avoids using one aggregate target as evidence for multiple consumers or trading established downscale quality for memory.

New integration tests are authored for shared API revision/lifetime ownership; fitted-RGBA parity and source/upscale native admission; image/video layout equivalence; default/unknown/shared/output-retirement routing; native last-good errors, pause/FPS/stale wakes and diagonal transition state. Three additional ignored Vulkan cases exercise the actual Element→Paint→Canvas path at integer/fractional density, clip/tint/opacity parity, frozen/live/RGBA transitions, and input rejection before publication. These integration tests have not yet been compiled or executed at this source checkpoint; the c4a results above cover the earlier independent painter only.

## Remaining quality and performance gates

Before production enablement we still need actual integrated GPU results and native streaming presentation; source-rate and whole-path memory comparisons with identical inputs/backends; ordinary metadata defaults consistent with established software behavior; and physical output/lifecycle testing. Native planes retain one-level bilinear sampling. The current slice protects minification through fitted RGBA fallback rather than claiming a native minification solution. A subsequent renderer implementation must choose filtering using each consumer's actual physical density/cover footprint, reuse bounded resources, preserve chroma siting/odd edges, and pass independent high-frequency downscale and HiDPI comparisons before it replaces that fallback. No heuristic multi-output aggregate can establish those guarantees. The twelve-load shader also requires actual throughput measurement before any source-rate claim. The retarget prototypes and recorded failures remain immutable.
